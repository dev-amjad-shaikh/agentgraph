| 1 | 🔴 | `llm.rs:714` | Correctness — SSE framing | `decoder.feed(&String::from_utf8_lossy(&bytes))` decodes each arbitrary TCP chunk independently. A multi-byte UTF-8 sequence split across `response.chunk()` boundaries becomes two U+FFFD replacement chars — **silent corruption of streamed non-ASCII content** (CJK, emoji, accented text). Ironically the SSE decoder is byte-chunk-agnostic (as its own doc says), but the UTF-8 boundary handling is not. | **Must fix.** Buffer raw bytes in `SseDecoder` and only `str::from_utf8` up to the last complete UTF-8 boundary (or buffer bytes and use `String::push_str` on validated slices). Add a test feeding a multi-byte char split across two `feed` calls. |
| 2 | 🔴 | `llm.rs:309-315` | Correctness — secret handling | `#[derive(Debug, Clone)]` on `OpenAiCompatibleClient` prints `api_key` **in cleartext** on any `{:?}` (logging middleware, panic messages, `dbg!`). Sibling-class issue to the secret-handling hunt. | **Must fix.** Hand-write `impl Debug` redacting the key (`api_key: Option<redacted>` → `"***"` when `Some`), or store the key in a wrapper type with a redacting `Debug`. |

| 6 | 🟡 | `mcp.rs:236-237`, `mcp.rs:198-212` | Correctness — resource bounds | `read_framed` trusts the peer completely: `Content-Length: 4_000_000_000` → `vec![0u8; len]` (multi-GiB host allocation → OOM), and newline-delimited mode buffers an unbounded line. A hostile or buggy MCP server (exactly the "untrusted ecosystem" this module targets) can kill the host process. | Cap both paths (e.g. 16 MiB default, configurable). Error, don't allocate, on oversized frames. |
| 7 | 🟡 | `mcp.rs:350` | Correctness — connection liveness | `Err(_) => break` — a **single malformed frame permanently bricks the client**: the reader task exits, every subsequent request fails with "connection closed while awaiting response", and nothing surfaces the parse error. For a long-lived stdio session this is a brittle failure mode with a confusing downstream symptom. | Log the malformed frame (tracing::warn) and either skip-and-resync (newline framing is self-resyncing) or fail the client *loudly and immediately* with a dedicated error, not a generic "connection closed". |
| 8 | 🟡 | `remote.rs` vs `llm.rs` | Idiom — retry/error-mapping consistency | Two HTTP clients, two philosophies: `RemoteNode` has timeout + classified retries + backoff; `OpenAiCompatibleClient` has **no retry at all** — a transient OpenAI 500/429 fails the whole agent run. Error bodies: llm.rs truncates to 512 chars (`chat completions returned {status}: ...`), remote.rs embeds the **full unbounded body** (`remote node ...: {status}: {body}`). Also 429/408 are classified Fatal in remote.rs — retryable by most conventions. | Extract/shared policy or at least align: truncate remote.rs bodies; treat 408/429 (with `Retry-After`) as retryable; give the LLM client the same Retryable/Fatal classification (it can reuse `AttemptError`-style logic). |
| 9 | 🟡 | `remote.rs:377-388` | Idiom — backoff quality | `base * 2^attempt`, no cap, no jitter. With `with_retries(20)` the last delay is `base * 2^19` (~14.5 h at the 100 ms default); concurrent agents retry in lockstep (thundering herd against the recovering worker). | Cap total/per-attempt delay; add jitter (`delay * rand(0.5..1.5)`); consider capping `attempt` shift (e.g. `min(attempt, 6)`). |
| 10 | 🟡 | `wasm_node.rs:264-270` | Correctness — sandbox gap | Guest-controlled `out_len` (low 32 bits of the packed return) is trusted for `vec![0u8; out_len]` — up to 4 GiB host allocation **before** `memory.read` can fail on OOB. A malicious guest (the raison d'être of this module) gets a cheap host-side memory-amplification DoS. | **Must fix.** Reject `out_len > memory.data_size(&store) - out_ptr` (or a hard cap) before allocating. Also add a test exercising `max_memory_bytes` enforcement — fuel exhaustion is tested, memory capping is not (coverage gap). |
| 11 | 🔵 | `llm.rs:533-551` | Correctness — SSE spec nit | A line of exactly `data` (no colon) means field `data` with empty value per the SSE spec (→ empty-string event); this decoder drops it. ## Positive notes (worth keeping)
- `SseDecoder` is otherwise a genuinely good hand-rolled state machine: CRLF handled, partial lines buffered across feeds, multi-line `data:` joined per spec, comment/heartbeat lines skipped, `[DONE]` + EOF fallback both handled, and *tested for the split-chunk case*. Finding #1 is the one real hole.
- `remote.rs` retry classification (`AttemptError::Retryable/Fatal`, worker errors & interrupts never retried) is exactly right and well-tested, including a hand-rolled mock HTTP server with hang/5xx/interrupt scenarios.
- `mcp.rs` request/response correlation is race-clean: pending inserted before write, removed on write-failure and timeout, late responses dropped harmlessly, reader-task drain wakes all waiters on EOF.
- `wasm_node.rs`: fuel metering + `ResourceLimiter` + empty `Linker` + per-call fresh `Store` + `spawn_blocking` is a sound sandbox posture; ABI validation fails fast at construction.
- Error mapping is uniformly into `AgentGraphError` variants with node/tool/mcp context prefixes; the `mcp:` prefix discipline is consistent.
- Examples are API-fresh: `RunConfig::with_resume`, `with_event_tx`, `Executor::with_checkpointer`, `JsonFileCheckpointer`, `Route::Send`, `Send::new`, `Reducer::{Overwrite,Append,AddMessages}`, `ctx.interrupt`, `ExecutionOutcome::state()` all verified against current `src/` — nothing stale in *usage* (only in *behavior*, see #5).
